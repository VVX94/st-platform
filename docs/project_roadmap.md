# 项目路线图

## 1. 项目定位

本项目旨在构建统一的平台底座，将分散的空间转录组算法组织成可注册、可调用、可比较、可复现的系统。

核心原则：

1. 先统一接口，再扩展算法数量
2. 先打通闭环，再扩展前后端复杂度
3. 先保证可复现，再追求大而全

## 2. 规划假设

- 适用场景：1-2 名开发者进行 MVP 开发
- 开发周期：建议 10-12 周完成第一轮迭代
- 首版数据范围：优先支持 `10x Visium` 数据
- 首版任务范围：优先支持 `QC`、`空间域检测`、`解卷积/映射` 三类任务
- 首版算法策略：每类任务接入 `1` 个代表算法和 `1` 个 baseline

## 3. MVP 范围

### 必做

- 统一数据对象抽象，兼容后续接入 `AnnData` / `SpatialData`
- 统一任务定义
- 统一算法注册机制
- 本地 runner
- 结果对象与运行记录
- 最小 CLI
- 单元测试和 demo

### 暂不做

- 完整 Web 平台
- 多用户系统
- GPU 集群调度
- 复杂数据库建模
- 全平台数据格式一次性兼容

## 4. 分阶段路线

## 阶段 0：范围冻结与技术选型

建议周期：第 1 周

工作项：

- 明确 MVP 只支持哪类数据
- 明确首批任务与算法名单
- 确定统一输入输出对象
- 确定项目代码规范、命名规范和测试基线
- 确定结果目录结构与运行记录格式

交付物：

- MVP 范围清单
- 算法接入名单 v1
- 结果文件规范 v1

验收标准：

- 每个人都能说清楚"首版做什么，不做什么"
- 至少形成一页任务-算法映射表

## 阶段 1：统一 Python 底座

建议周期：第 2 到 4 周

工作项：

- 建立包结构
- 建立 `SpatialDataBundle` 等核心数据对象
- 建立 `TaskDefinition` / `TaskCatalog`
- 建立 `AlgorithmSpec` / `AlgorithmRegistry`
- 建立 `LocalRunner`
- 建立 CLI 演示入口

交付物：

- 可安装或可直接运行的 Python 包
- 可执行 demo
- 基础单元测试

验收标准：

- 能用统一命令列出任务和算法
- 能以同一套接口调用至少 2 个 demo 算法
- runner 返回统一结果对象

## 阶段 2：首批算法接入

建议周期：第 5 到 7 周

工作项：

- 接入 1 个空间域检测算法
- 接入 1 个解卷积或映射算法
- 接入 1 个基础 QC / 预处理流程
- 建立参数模板与默认配置
- 建立输入检查与失败信息规范

交付物：

- 算法适配器
- 统一参数模板
- 统一错误处理规范

验收标准：

- 至少 3 个真实算法或 baseline 能通过统一接口执行
- 任务与算法的匹配关系有清晰约束
- 失败日志可定位到输入、参数或环境问题

## 阶段 3：结果规范与评测模板

建议周期：第 8 到 9 周

工作项：

- 定义结果对象 schema
- 统一指标模板
- 统一日志格式
- 输出最小 benchmark 流程

交付物：

- `metrics` 模板
- `artifacts` 目录规范
- 基准数据与示例报告

验收标准：

- 同类任务算法能在统一结果结构下比较
- 一次运行至少包含参数、时间、日志、指标、产物索引

## 阶段 4：最小 API / UI 闭环

建议周期：第 10 到 11 周

工作项：

- 加一层最小 API
- 提供上传数据、选择任务、选择算法、提交运行的流程
- 做一个基础结果页，优先展示空间图、UMAP、指标摘要

交付物：

- 最小后端接口
- 最小前端页面或 notebook-style dashboard

验收标准：

- 非开发者可以完成一次 demo 数据运行
- 结果页能看到至少 1 个图、1 组指标、1 条运行记录

## 阶段 5：工程化增强

建议周期：第 12 周及以后

工作项：

- 任务队列
- 容器化 runner
- 多环境隔离
- 结果持久化
- 多用户与权限
- 部署脚本

交付物：

- Docker 化执行方案
- 异步任务模型
- 结果与日志持久化策略

验收标准：

- 同一平台可稳定运行多个任务
- 算法环境冲突不再污染主环境

## 5. 本周就能启动的待办

### P0

- 把当前骨架跑通
- 冻结 MVP 数据范围
- 确定首批算法清单
- 定义统一结果目录结构

### P1

- 接入真实 `Visium` demo 数据读取器
- 补 `AnnData` / `SpatialData` 适配层
- 把参数模板改成配置文件驱动

### P2

- 设计最小 API
- 设计结果页原型

## 6. 风险与建议

### 风险 1：过早支持过多平台

建议：

- 首版仅支持 `Visium`
- 后续扩展到 `Xenium / CosMx / GeoMx`

### 风险 2：算法接入过多导致接口不稳定

建议：

- 先接入最少数量，但严格把控接入标准

### 风险 3：过早开发完整 Web 而底层不稳

建议：

- UI 在阶段 4 开始，仅实现最小闭环

## 7. 第一轮里程碑

### 里程碑 M1

时间：第 4 周末

标准：

- 底座包结构稳定
- demo 任务执行跑通
- 单测通过

### 里程碑 M2

时间：第 7 周末

标准：

- 接入 3 个首批算法
- 参数模板与结果模板稳定

### 里程碑 M3

时间：第 11 周末

标准：

- 一个最小 UI / API 演示闭环可用

## 8. 完成标准

首版完成需同时满足以下条件：

1. 具备统一任务模型，而非脚本堆叠
2. 具备统一算法注册与调用机制，而非手工分支逻辑
3. 具备统一结果对象，而非各算法各自输出
4. 具备基础测试，确保后续算法扩展不会破坏底座
5. 至少有一条从数据到结果的最小演示链路
